코드 리뷰란?

코드 리뷰가 필요한 이유

https://yozm.wishket.com/magazine/detail/1957/

예전에는 코드 리뷰의 중요성을 잘 몰랐다. 개발자 개개인이 잘 짜야 하는 문제라 생각했다. 하지만 MSA처럼 여러 마이크로서비스가 얽혀서 동작할 때는 서로 확인해주는 것이 중요하다. 개개인이 잘 짜야 하는 문제라고 정의했을 때는, 사고가 나도 개인의 책임으로 돌리게 되고, 그 개인은 감추려고 한다. 즉, 서로 감추고 헐뜯고 책임을 전가하는 문화가 만들어져버린다. 서로가 함께 책임을 떠안아야 하는 문제라고 정의했을 때는, 문제를 드러내고 서로 확인해주는 문화가 생긴다. 일단은 나 혼자서라도 코드를 다 보자. 물론 남이 짠 코드는 내 눈에 잘 들어오지 않는다. 업무 지식이 부족할 때는 더더욱 그렇다. 그래도 안 하는 것보다는, 내가 할 수 있는 만큼만 하더라도, 안 하는 것보다는 효과가 훨씬 높다.

→ 처음부터 전체 코드를 보고자 할 필요는 없다. 일단은 관심 있는 항목만 가볍게 훑어 보며 리뷰를 하다가 관심이 생기는 부분만 대화를 해보는 것에서 출발해도 충분하다.

경험이 부족한 개발자들은 당장의 답만 찾는 경우가 많은데, 이 경우 소통에 어려움이 있을 수 있다.

→ 사람은 자기가 관여한 경험과 결부된 지식을 쉽게 기억한다. 즉, 코드 리뷰에 참여할 경우 지식은 효과적으로 살아남고 전달된다.

다른 회사는 어떻게 코드 리뷰를 하고 있을까?

화해

https://blog.hwahae.co.kr/all/tech/12534

내용

코드리뷰의 목적

  • 서비스 안정성 보장
  • 업무 효율 증대
  • 지식 공유 및 코드 품질 향상

리뷰 마니또

  • 구성원은 본인이 속한 도메인 인원 1명에게 마니또로 지정된다
  • 마니또로 지정된 사람은 요청받은 테크스펙과 PR 리뷰에 필수 참여한다
  • 마니또는 매월 첫째 주에 봇으로 선정하며 1달간 유지한다
  • 리뷰 요청자는 리뷰를 수월히 진행할 수 있도록 컨텍스트 설명과 질의응답 등 지원을 아끼지 않는다
  • 동일한 사람이 리뷰어로 지정되지 않도록 리뷰 마니또는 랜덤으로 선정한다

리뷰 코멘트 템플릿

코드리뷰 시 코멘트 중요도를 측정 가능한 레벨로 표기하여 커뮤니케이션 비용을 줄이는 것

  • L0

    리뷰불가

    • PR Description, 테크 스펙 등 어떤 작업을 했는지 충분한 설명이 없는 경우
    • 변경 작업이 너무 커서 리뷰가 어려운 경우
    • 설계가 잘못되어 전체적으로 재작업이 필요하다고 판단해 리뷰를 진행할 수 없는 경우

  • L1

    변경요청

    • 기능 결함, 심각한 퀄리티 저하, 팀 컨벤션 위반 등 반드시 머지 전에 변경이 필요한 경우

  • L2

    변경협의

    • 가급적 머지 전에 변경되었으면 좋겠지만, 배포 후 후속 작업으로 바로 진행이 된다면 괜찮다고 생각하는 경우
    • 작성자가 의견에 동의하지 않는다면 토론 필요

  • L3

    중요질문

    • 궁금증이 해소되어야 정확한 리뷰/피드백이 가능하다고 판단하는 경우

  • L4

    변경제안

    • 제시한 방안이 더 좋다고 생각하지만 작성자 판단에 맡겨도 무관한 경우

  • L5

    참고의견

    • 더 좋은지는 모르겠으나 다른 방법 제시 혹은 참고할만한 내용인 경우

리뷰 요청자 코멘트

리뷰를 요청한 사람이 미리 다른 개발자가 궁금해할 법한 내용을 코멘트로 추가해두면 코드리뷰 비용을 줄일 수 있음

이외 코드리뷰 비용을 줄이는 방법

  1. 테크스펙 작성

    • 명확한 목표 설정
    • 요구사항 파악
    • 설계 구체화
    • 팀원 간 의사소통
    • 개발 비용 절약

  2. 테스트 코드 작성

    로직 변경 시 관련 테스트 코드가 없으면 코드 병합 불가

  3. 실시간 피드백 필요 시 페어 프로그래밍 진행

뱅크샐러드

https://blog.banksalad.com/tech/banksalad-code-review-culture/#순리

내용

작은 PR 규칙

1개의 PR은 1,000 Line을 넘을 수 없다

  • PullRequest, Commit의 단위는 최소의 기능 단위로 세분화한다
  • 테스트 코드는 제한을 두지 않는다

→ 개발 기능의 복잡도에 따라 코드의 길이가 길어지고, 이에 따라 리뷰어의 집중도가 떨어지기 마련

코드 리뷰가 고객 임팩트를 내는 부분에 있어 병목이 되지 않도록 하기 위함

실험 플랫폼

가설을 발굴하고 실험을 통해 검증하는 과정을 통해 새로운 기능 출시

→ 이전에 시도해보고 싶어 제안했던 트렁크 기반 개발과 유사하다고 생각

  • 실험 기능의 개발, 실험의 진행은 실험 플랫폼이 있는 동일한 메인 브랜치에서 진행
  • 전체 기능 개발이 완료되지 않더라도 최소 기능의 PR의 리뷰가 완료되면 메인에 merge
    • 노후화 및 Conflict 방지

GitHub Template 활용

리뷰 요청자의 준비물

  • 제품 기능 기획
  • 기술적인 구현 계획
  • 현재 PR에서의 변경점
  • 예상/구현된 디자인
  • 어떤 내용들을 테스트했는지/해야 하는지 목록

코드 리뷰 과정에서 이루어지는 것

  • 일관된 아키텍처를 유지하고 있는지
  • 다른 해결 방법에 대한 의견 제시
  • 버그가 발생할 수 있는 가능성 제시
  • 기술적인 지식, 노하우 공유
  • 히스토리 전달

  • P2

  • P3

  • P4

  • P5

  • D-N

    Working Day 기준으로 N일 이내에 리뷰 필요
